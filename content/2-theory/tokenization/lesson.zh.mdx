第 11 关的模型预测的是下一个**词**。但“词”只是一种选择。模型读的是一列 **token**，
总得有人决定一个 token 在哪里结束、下一个从哪里开始。这个选择决定了词表的大小、
每个序列的长度，以及模型到底能读哪些文本。

每个不同的 token 都有一个 **id**，是从 0 到词表大小减 1 之间的一个数。第 13 关会把 id 变成向量。

## 3. 字节对编码：让数据来决定

**BPE**（byte-pair encoding，字节对编码）从字符开始，把经常一起出现的片段拼成更大的 token：

1. 把每个词切成字符。
2. 在所有词上数出每一个相邻 token 对，按每个词出现的次数加权。
3. 把最常见的一对合并成一个新 token，加进词表。
4. 从第 2 步开始重复，想重复几次都行。

## 4. 合并多少次？

每次合并给词表加一个 token，并让序列变短。在 40 个生成的词上：
合并之前有 19 个字符、1,068 个 token；合并 40 次之后，词表有 59 个条目，这些词只占 263 个 token。
token 越少，每段文本要做的计算就越少。这也意味着模型的**上下文窗口**（context window）能装下更多文本：
模型一次最多读固定数量的 token，所以每段文本越短，模型能看到的就越多。

大词表也有代价。模型有一张**嵌入表**（embedding table）：一张普通的表，每个 token 一行数字
（第 13 关会讲它怎么用）。每个 token 在那里都要有自己的一行，在给下一个 token 打分的最后一层里也要有自己的一列。

<Blank id="emb-params" />

<Deeper title="真实的分词器有什么不同">

- **它们从字节开始，而不是从字符开始。** 每段文本都是一列字节，取值 0 到 255，所以起始词表
  是 256，并且永远不会有未知的东西：一个表情符号或一种少见的文字只是变成几个字节 token。
- **空格粘在词上。** 文本先被切开，让空格跟着它后面的词走，所以 "␣cat" 和 "cat"
  是不同的 token。这样解码时空格能完全还原。
- **几万次合并。** 真实的词表大约有 30,000 到 200,000 个 token。常见的词变成一个 token；
  少见的词变成两到五个片段。

思路和实验台一样：数相邻对，合并最常见的，重复。

</Deeper>

<Stuck q="为什么模型不擅长拼写、数字母，或者对很长的数做算术？">

因为它们从来看不到字母。像 "chatting" 这样的词可能以两个 token 的形式到来，比如 "chat" 和 "ting"。
模型拿到的是两个 id，而不是八个字符。要数出有几个 t，它必须学会每个 token 里面有什么。

数字也是用同样随意的方式切的："12345" 可能变成 "123" 和 "45"，而 "12346" 的切法又不一样。
从一个数到另一个数，各位数字不在同样的列上，这让逐列做算术变得很难。
有些模型的解决办法是总把数字切成单个的数字。

</Stuck>
