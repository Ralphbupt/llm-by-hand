## 任务

- **模型做什么。** 它读入 `<bos>23+58=`，接着写出 `81<eos>`。每个字符一个 token。
  `<bos>` 是起始 token：每个序列都以它开头，这样模型在第一个数字之前就有输入。
  `<eos>` 是结束 token：答案写完时，模型写出它。
  聊天模型写东西的方式正是这样：一次又一次地预测下一个 token。
- **数据。** a、b 从 0 到 99 的每一对：10,000 道题。把它们打乱。用 8,500 道训练。用 500 道做验证，
  挑出最好的那一轮。最后 1,000 道单独放着：模型从来看不到它们，你也不根据它们做任何选择。
- **词表。** 15 个 token：`<pad>`、`<bos>`、`<eos>`、十个数字、`+` 和 `=`。
- **模型。** 仅解码器：嵌入，几个由因果自注意力和 FFN 组成的块，然后是输出层。
  没有编码器，也没有交叉注意力。块是 **pre-norm**（第 16 关），用 **RMSNorm**（第 19 关），
  位置嵌入是学出来的。
- **通关条件。** 两项检查。第一，你的代码载入固定权重，必须算出和参考实现一样的 logit。
  第二，你训练好的模型写出 1,000 道没见过的题的答案，至少 950 道必须全对。

按顺序做这些步骤。每一步都有一个检查，在你把某个部件用到下一步之前，先告诉你它是对的。

## 第 1 步：数据，错开一位

每个 token 都有一个 id。这一页的检查用的是这些 id：

| token | `<pad>` | `<bos>` | `<eos>` | `0` … `9` | `+` | `=` |
|---|---|---|---|---|---|---|
| id | 0 | 1 | 2 | 3 … 12 | 13 | 14 |

所以数字 2 的 id 是 5，数字 8 的 id 是 11。拿 23 + 58 这道题来说。写成一个 token 序列，它是
`<bos>23+58=81<eos>`。

<Stuck q="view 报错：“view size is not compatible with input tensor’s size and stride”。">

`view` 只是按数在内存里的排列重新标记它们，从不移动它们。`transpose` 之后，本该挨在一起的数
在内存里并不挨在一起，所以 `view` 拒绝了。`.contiguous()` 会按新顺序复制一份，
然后 `view` 就能用了。`.reshape(B, L, d_model)` 会替你把两步都做了。
报错是：`view size is not compatible with input tensor's size and stride … Use .reshape(...) instead.`

</Stuck>

<Stuck q="我的模型能跑，但训练时有些块从来不变。">

检查你是怎样存这些块的。模型是一个类：`__init__` 搭好各个部件，`forward` 使用它们。
只有部件被存成模块（module），PyTorch 才找得到它的权重。普通的 Python 列表会把它藏起来：
`self.blocks = [Block(...), Block(...)]` 能正常运行，但 `model.parameters()` 看不到这些块，所以优化器
从不更新它们。用 `nn.ModuleList([...])`。单个学出来的数也要同样小心：用
`nn.Parameter(...)` 包起来，就像 RMSNorm 的增益那样，否则它也不会被训练。

</Stuck>

## 第 3 步：过拟合一批数据

取 8 个固定的样本，只用它们训练 300 步。正确的模型会把它们背下来：
损失只算答案数字时，参考实现从 2.73 降到 50 步后的 0.061，300 步后的 0.003。

第一个数不是随便来的。训练之前，模型给 15 个 token 中的每一个差不多相同的概率，
1/15。损失是 −ln(1/15) = ln 15 ≈ 2.71。所以没训练过的模型应该从 2.7 附近开始。

<Predict id="start-loss" />

如果一批数据上的损失一直很高，bug 在你的代码里，而不是模型的大小。几乎总是这三样之一：
因果掩码、错开一位，或者损失在数什么。

<Stuck q="我在一批数据上的损失停在 0.22 左右，降不下去了。">

检查你是不是在每个位置上都算了损失。参考实现正是这样做的：50 步后 0.36，
然后停在 0.22。`<bos>` 之后，8 个样本以不同的数字开头，前面没有任何 token 告诉模型第一个数字是什么。
没有哪个模型能猜对这些，所以损失降不到那个水平以下。
每个样本在它的第一个数字上损失 ln 8 ≈ 2.08。分摊到每个样本大约 9.5 个目标值上，就是 ln 8 / 9.5 ≈ 0.22。

改成损失只算答案数字，同一个模型就降到 0.003。
你的模型没问题。是这个测试要它去猜一个随机数字。

</Stuck>

<Stuck q="算损失那一行报错：“Expected target size [8, 15], got [8, 10]”。">

`F.cross_entropy` 要求每个预测一行分数，但你的 logit 是 (8, 10, 15)：8 个样本、10 个位置、
15 个 token。像第 17 关那样把它们摊平成每个位置一行：
`F.cross_entropy(logits.reshape(-1, 15), y.reshape(-1), ignore_index=IGNORE)`。这是 80 行、每行 15 个分数，以及 80 个目标值。

</Stuck>

## 第 4 步：训练

用 8,500 道训练题训练，批大小 64，学习率 0.001 的 Adam。一**轮**（epoch）就是把 8,500 道题
全部过一遍，每次用新的随机顺序。训练 40 轮，在笔记本电脑上大约一分钟。每一轮之后，
在 500 道验证题上测准确率。准确率可能会降一两轮然后恢复，所以要保留
最好的模型。每当验证准确率超过目前最好的成绩，就把模型存下来给检查用。起始文件里的 `train` 写了
做这件事的那一行。如果连最好的一轮都低于 95%，就多训练几轮（比如 60 轮）。

<PlateauLab />

<Stuck q="为什么准确率好几轮都不变，然后突然跳上去？">

准确率只算完全正确的答案。一个答对三位中两位的模型得零分。
在平的那一段，模型在学一些零碎的东西：答案有两位或三位，最后一位取决于
a 和 b 的最后一位。训练损失能看出这一点。损失算每个位置时，它在第 4 轮到第 8 轮之间从 1.34 降到 1.27，
而准确率只是慢慢地从 8% 升到 15%。

然后模型把这些零碎的东西组合起来，包括进位。进位就是某一列加起来达到 10 或更多时，挪到下一位的那个 1，
比如 8 + 5 = 13。这之后，整个答案开始答对。
平的那一段持续多久，取决于模型、数据和设置。在别的设置下，它可能持续五十轮。

</Stuck>

**是平台期还是 bug？** 看训练损失，不要只看准确率。

- **损失还在下降：** 模型在学。继续训练，即使准确率还没动。
- **损失已经平了很久，而且过拟合一批数据（第 3 步）也失败：** 这是 bug。用
  一个很容易的任务训练，比如第 17 关的复制任务，先修好代码，再去训练更久。

<Stuck q="我跑了两次，得到的数一模一样。不是应该随机吗？">

`torch.manual_seed(0)` 把每个随机选择都固定住了：初始权重、批的顺序和数据划分。
这是故意的。在实验里改一样东西时，你看到的变化就来自这一样东西。
想看随机性有多大影响，就换一个随机种子：平的那一段会变长或变短，最终结果差不多。

</Stuck>

<Deeper title="为什么损失只算答案数字时起步更快">

损失算每个位置时，大部分目标值是 a 和 b 的数字。它们是随机的，模型学不会，
而每一批的梯度大部分都来自它们。损失只算答案数字时，全部梯度都在推着模型去学会正确地做加法。

在这两次训练里，损失只算答案数字的那次早期遥遥领先：8 轮后 81%，而算每个位置的只有 15%。
它也稍早一点达到 95%（第 14 轮对第 16 轮）。两次最后都接近 100%。两条曲线都不平滑：
损失只算答案数字的那次在第 18 轮掉到 84.2%，然后又恢复了。先看几轮，再判断一次训练是好是坏。

</Deeper>

## 第 5 步：评估，打败 Boss

对每道没见过的题，把 `<bos>a+b=` 交给模型，选出分数最高的 token，接在后面，重复直到 `<eos>`。
只有每一位都对，答案才算对。

不要只看分数。98% 的模型仍然会答错 20 道题，而答错的那些常常有共同点。
把每一道错题打印出来，找出规律。`zip` 把两个列表一起读，一次读一对：
`list(zip([1, 2], ["a", "b"]))` 是 `[(1, "a"), (2, "b")]`。
